    API とは何か：チャットの画面との違い

    はじめる所要 約25分

    この章で分かること

    1. API（application programming interface）が何かを、「プログラムから使う入口」として説明できる。
    2. チャットの画面で使う Claude と、API で使う Claude の違いを、操作する人・会話の記憶・料金・責任の 4 点で言える。
    3. API を使うと何ができるようになるかと、この講座で扱う範囲を言える。

    前提：序章だけです。プログラミングの経験は要りません。

    API とは、プログラムから使う入口

    API（application programming interface）は、あるサービスの機能を、別のプログラムから使うための入口です。レストランに例えると、メニューと注文の決まりのようなものです。決まった形で注文を出せば、決まった形で料理が届きます。

    Claude API は、Claude を自分のプログラムから使う入口です。公式ドキュメントは、Claude API を、https://api.anthropic.com にある REST 型の API と説明しています。文章を決まった形で送ると、Claude の答えが決まった形で返ります（出典：API overview、2026 年 11 月 18 日確認）。

    決まった形のやり取りを、リクエスト（request、送る側）とレスポンス（response、返る側）と呼びます。形式は JSON（JavaScript Object Notation）という、項目と値を波かっこで囲む書き方です。第 03 章で、実物を 1 つずつ読みます。

    図の部品を押すと、役割が出ます。あなたのプログラムが、API にリクエストを送り、API がモデル（Claude）に処理を頼み、結果がレスポンスとして返ります。API キーと支払いは、Claude Console（Anthropic の管理画面）で管理します。

    チャットの画面との違い

    チャットの画面では、人が文章を入力し、画面に答えが出ます。API では、プログラムが文章を送り、プログラムが答えを受け取ります。人が見ていなくても動かせるので、仕事の仕組みに組み込めます。

    表で大事なのは、右の列の「自分のプログラムが受け持つ」ことです。会話の記憶、入力の準備、答えの確認、エラーへの対応は、自分の仕組みで決めます。画面では、これらが画面の機能として用意されています。

    API で何ができるようになるか

    文章を入れて、文章が返る仕組みなので、文章に関する仕事の多くが対象になります。たとえば、下書きの作成、要約、書類からの項目の抜き出し、分類、翻訳、コードの説明です。第 12 章で、7 つの利用例を、人の確認の位置まで含めて学びます。

    公式ドキュメントの API の概要には、メッセージを送る Messages API のほかに、まとめて処理する Message Batches API、トークンを数える Token Counting API、モデルを一覧する Models API、ファイルを預ける Files API があります（出典：API overview）。この講座は、このうち、第 03 章から Messages API を中心に使い、第 05 章と第 10 章で、ほかの 3 つにも触れます。

    この講座の範囲

    Claude は、AWS・Google Cloud・Microsoft Azure のサービスからも使えます（出典：API overview）。この講座は、Anthropic が直接提供する Claude API だけを扱います。クラウド経由では、機能の提供の時期や料金の払い方が違うことがあります。

    つまずきやすい点

    画面で Claude を使えている人でも、API は別の入口です。API には、Console でのキーの作成と、支払いの設定が要ります（第 02 章）。また、API は「前の会話を覚えている」前提で動きません。続きを話すには、これまでの会話を毎回送ります（第 04 章）。

    準備：アカウント・API キー・支払いと上限

    はじめる所要 約35分

    この章で分かること

    1. アカウントの作成から API キーの発行までの準備の流れを、順に言える。
    2. API キーを安全に扱う方法（環境変数、公開の場所に置かない）と、漏れたときの対応を説明できる。
    3. 支払い（前払いのクレジット）と、利用の上限を設定する目的を説明できる。

    前提：第 01 章。この章の操作は、Web の画面（Claude Console）と、ターミナルの 1 行のコマンドだけです。

    全体の流れ：6 つの準備

    最初の 1 回を送るまでに、6 つの準備があります。順番に意味があります。お金の上限を決めてから、キーを作ると、間違えて使いすぎる心配が小さくなります。工程を押すか「次へ」で進んでください。

    アカウントは、Claude Console（platform.claude.com）で作ります。公式のクイックスタートは、最初に「Claude Console のアカウントを作るか、持っていればサインインする」ことを求めています。API キーは、Console の API キーのページで作ります（出典：Get started with Claude、2026 年 11 月 18 日確認）。

    API キーとは何か

    API キー（API key）は、「このリクエストは、このアカウントからです」と示す、長い文字列です。パスワードに近いものです。キーを持っている人は、あなたの費用で API を使えます。だから、他人に見せないのが基本です。

    キーを作るときの要点は、公式ドキュメントの「Get your Claude API key」にあります。Console の「Create key」で、キーの名前を付け、有効期限を選び、「Linked account」（誰に結びつけるか）を選びます。同じ画面で、キーを使えるワークスペース（組織の中の作業領域）を 1 つ選んで、キーをそこに限定できます。公式ドキュメントによると、ワークスペースに限定しないキーでは、リクエストのたびに anthropic-workspace-id ヘッダー（ワークスペースの ID）も送る必要があります。この講座の第 03 章の例は、このヘッダーを付けていないので、はじめはワークスペースを 1 つ選んで作るのが簡単です。完全なキーは、作った時に 1 回だけ表示されます。なくすと、もう見られず、新しく作り直します（出典：Get your Claude API key、Authentication）。

    なお、公式のクイックスタートは、自分のパソコンでの開発には、Anthropic のコマンドラインツールでサインインする方法を勧めています。この講座は、仕組みに組み込むときにも使う、API キーの方法で説明します（出典：Get started with Claude）。

    キーは 1 回しか見えません

    作った画面を閉じる前に、安全な場所（秘密情報を管理する仕組み）に保存してください。この講座の例には、キーの実物は書きません。「YOUR_API_KEY」のような、仮の言葉を使います。

    キーの安全な扱い

    安全に扱う基本は、キーをコードに書かず、環境変数から読むことです。環境変数（environment variable）は、パソコンの設定に名前をつけて値を入れておく仕組みで、プログラムから読めます。公式の SDK は、ANTHROPIC_API_KEY という名前の環境変数を自動で読みます（出典：Get started with Claude）。

    # macOS / Linux のターミナル（この 1 回のウィンドウだけで有効）
export ANTHROPIC_API_KEY="YOUR_API_KEY"

# Windows の PowerShell（この 1 回のウィンドウだけで有効）
$env:ANTHROPIC_API_KEY = "YOUR_API_KEY"

    公式ドキュメントが示す書き方は、export ANTHROPIC_API_KEY=… の形です。PowerShell の書き方は、OS の一般的な方法で、公式の API ドキュメントの記載ではありません。ウィンドウを閉じると消えるので、毎回入れ直すか、OS の設定に保存します。保存の方法は、お使いの OS の説明を見てください。

    表の左が安全な扱い、右が避ける扱いです。特に、Web ページの JavaScript にキーを入れないことが大事です。公式ドキュメントは、「Claude API は自分のバックエンドから呼ぶ。利用者のブラウザで動くコードから呼ばない。ページを使う人は誰でも、ページのコードの中のキーを読めるから」と説明しています（出典：Authentication）。

    漏れたときの対応

    キーが漏れた、または漏れたかもしれないときは、先に止めて、あとで調べるのが基本です。公式ドキュメントでは、キーの管理のページで「Disable」（無効にする。あとで戻せる）と「Delete」（削除する。戻せない）を選べます。疑いがあるキーは、無効にするか削除します（出典：Authentication）。

    支払いと利用の上限

    API の利用料は、使った分だけかかります。支払いの方法は、公式のサポート記事によると、多くの組織で前払いのクレジットです。「Claude API とプレイグラウンドの利用は、前払いの利用クレジットで請求される」と書かれています。月ごとの後払いの契約もあります。クレジットは Console の「Billing」ページで買います。クレジットの残りが少なくなると自動で買い足す「自動リロード」も設定できます。クレジットは、購入から 1 年で期限が切れ、返金はされません（出典：サポート記事「How do I pay for my Claude API usage」、確認 2026 年 11 月 18 日）。

    新しいユーザーは、試すための無料のクレジットをもらえる、と公式の料金ページに書かれています（出典：Pricing の FAQ）。内容は変わることがあるので、Console で確かめてください。

    次に利用の上限（spend limit）です。公式ドキュメントによると、使える上限は 2 つの層があります。1 つは、利用の段階（tier）ごとに決まった月の上限です。もう 1 つは、自分で、その下に決める上限です。Console の「Spend limits」のページで、月の上限を設定できます。自分で決めた上限に達すると、API のリクエストは HTTP 400（invalid_request_error）で止まります。上限を上げるか外すと、再開できます（出典：Rate limits）。上限の金額の例は、第 05 章の 1 か所に書きました。

    最初の設定の目安（この講座の見方）

    はじめは、「使ってもよい金額」を、小さく決めてください。プログラムの書き間違いで、同じリクエストを繰り返し送ってしまう失敗は、よくあります。上限は、そのときの損害を小さくするための安全装置です。

    メッセージの形と、会話の続け方

    仕組み所要 約40分

    この章で分かること

    1. リクエストのメッセージの形（system、user、assistant の置き場所）を説明できる。
    2. API が会話を覚えていないこと、会話の続きは履歴を毎回送って作ることを、コードで確かめられる。
    3. 実験台で、部品（system、会話の長さ、ツール、構造化した出力、ストリーミング）を選び、リクエストの JSON の形が変わることを確かめられる。

    前提：第 03 章。リクエストの本文（model、max_tokens、messages）を読めること。

    メッセージの 3 つの置き場所

    リクエストの本文で、会話に関わる部品は 3 つです。system（役割や決まりを書く場所）、user（利用者の発言）、assistant（モデルの過去の答え）です。user と assistant は、messages の一覧の中に、交互に並べます。system は、messages の外の、本文のトップレベルに書きます（出典：Messages API reference、Working with Messages、2026 年 11 月 18 日確認）。

    補足：公式ドキュメントには、会話の途中で指示を足すために、messages の中に role が system の発言を置く方法もあります。置けるのは user の発言の直後だけで、messages の先頭には置けません。対応するモデルも決まっています（出典：Working with Messages）。最初から効かせたい指示は、これまでどおりトップレベルの system に書きます。この講座では、トップレベルの書き方だけを使います。

    1 つの発言の content は、ただの文章でも書け、ブロックの一覧でも書けます。画像や PDF を付けるときや、ツールの結果を返すときは、ブロックの一覧にします（第 09 章・第 10 章）。

    API は、会話を覚えていない

    公式ドキュメントは、Messages API を「ステートレス」と説明しています。ステートレス（stateless）とは、前のやり取りを覚えていない、という意味です。だから、会話の続きを話すには、これまでの会話の全部を、毎回送ります（出典：Working with Messages）。モデルの側では、前の呼び出しの内容は残っていません。公式ドキュメントには、API の側で会話を保持するベータ機能（message threads）も載っていますが、この講座は、履歴を毎回送る基本の形だけを扱います。

    次の Python は、会話の履歴を自分で持ち、毎回全部を送る、最小の例です。

    import anthropic

client = anthropic.Anthropic()
history = []  # これまでの会話。毎回、全部を送る


def ask(text):
    history.append({"role": "user", "content": text})
    message = client.messages.create(
        model="claude-haiku-5-5",
        max_tokens=1000,
        system="あなたは、丁寧で簡潔に答える日本語のアシスタントです。",
        messages=history,
    )
    answer = "".join(b.text for b in message.content if b.type == "text")
    history.append({"role": "assistant", "content": answer})
    return answer


print(ask("パスタを茹でるとき、塩はなぜ入れますか。"))
print(ask("入れすぎると、どうなりますか。"))  # 「入れすぎる」の対象を、履歴から読み取れる

    2 回目の質問は「入れすぎると」としか書いていません。それでも答えられるのは、履歴に 1 回目の質問と答えが入っているからです。履歴が長くなるほど、毎回送る量が増えます。送る量は、費用にも関わります（第 05 章）。

    実験台：リクエストの組み立て

    部品を選ぶと、リクエストの JSON に何が加わるかが変わります。まず、ボタンで「最小の呼び出し」から順に押してみてください。下のつまみで、会話の長さや、1 つの発言の文字数も変えられます。右の図は、呼び出しのたびに、送る文字数が増えていく様子です。

    実験台で見る点は 3 つです。1 つ目は、必須の 3 つ（model、max_tokens、messages）は、どの組み合わせでも残ることです。2 つ目は、system は messages の外に出ることです。3 つ目は、会話が続くほど、送る文字数が増えることです。文字数は架空の仮定の値です。

    assistant の書き出しを指定する方法は、使えなくなった

    古い記事には、最後の assistant の発言に、書き出しの文章を入れておき、続きを書かせる方法（プレフィル、prefill）が出てきます。公式ドキュメントによると、この方法は、Claude 4.6 以降のモデルではサポートされず、使うと 400 エラーになります。代わりに、構造化した出力（第 08 章）か、system プロンプトの指示を使うよう案内されています（出典：Working with Messages）。

    つまずきやすい点

    1 つ目は、user と assistant を交互に並べないことです。API リファレンスによると、モデルは user と assistant が交互に並ぶ会話で学習されていて、同じ役の発言が続くと、1 つの発言にまとめられます。エラーにはならなくても、意図と違う会話として読まれることがあるので、交互に並べます。2 つ目は、最初からの指示を messages の先頭に、role を system として書くことです。トップレベルの system に書きます（role が system の発言は、先頭には置けません）。3 つ目は、履歴を送り忘れて、「前の話を覚えていない」と戸惑うことです。API の仕様どおりの動きです。

    トークンとは何か

    トークン（token）は、モデルが文章を読み書きするときの、文字の小さなかたまりです。単語・単語の一部・文字・バイトなどに対応します。公式の用語集によると、Claude では、1 トークンが何文字にあたるかは、モデルと言語によって違います（出典：Glossary、2026 年 11 月 18 日確認）。

    トークンは、入力と出力に分けて数えます。入力トークンは、送った内容（system、履歴、質問、資料）で、出力トークンは、モデルが作った答えです。第 03 章の usage に、2 つの数が出ていました。

    文字数からトークン数を求める換算は、正確にはできません。公式ドキュメントが示す目安は、次のとおりです。

    • 以前のモデルでは、1 トークンは、英語でおよそ 3.5 文字です。
    • Claude 4.7 以降のモデル（この講座で扱う 4 つのモデルを含む）は、新しいトークナイザー（文章をトークンに分ける仕組み）を使い、同じ文章で、約 30% 多くのトークンになります。
    • 日本語の換算値は、確認できた公式ドキュメントには書かれていません。

    日本語の文章のトークン数は、自分の文章で測るのが確実です。公式の「トークンカウント」の機能は、無料で、送る前にトークン数を数えられます。数えた値は推定値で、実際の入力トークン数と、わずかに違うことがあります（出典：Token counting）。

    import anthropic

client = anthropic.Anthropic()

count = client.messages.count_tokens(
    model="claude-sonnet-5-5",
    system="あなたは、丁寧に要約する日本語のアシスタントです。",
    messages=[{"role": "user", "content": "ここに、数えたい文章を入れます。"}],
)
print(count.input_tokens)  # 送ったとして、入力が何トークンになるかの推定

    料金表の読み方

    料金は、100 万トークン（MTok）あたりのドルで表されます。たとえば、1 MTok あたり 2 ドルなら、100 万トークンの入力に 2 ドルかかります。1 回の費用は、次の式です。

    費用（ドル）＝（入力トークン数 × 入力の単価 ＋ 出力トークン数 × 出力の単価）÷ 1,000,000

    表で気づく点は 3 つです。1 つ目は、入力と出力で単価が違うことです。2 つ目は、キャッシュの読み取りが、入力の単価より安いことです（第 10 章）。3 つ目は、バッチ処理が、入力も出力も半額になることです（第 10 章）。Claude Haiku 5.5 は、1 回のリクエストの入力が 100,000 トークンを超えると、高い単価になります。公式の料金ページは、この区切りを、モデルの行を分けて示しています（出典：Pricing）。

    コンテキストウィンドウ

    コンテキストウィンドウ（context window）は、1 回の呼び出しで、モデルが扱える量の上限です。入力と出力の両方が含まれます。この講座で扱う 4 つのモデルは、公式のモデル一覧によると、100 万トークンのコンテキストウィンドウと、128,000 トークンの出力の上限を持ちます。入力だけで上限を超えると、API は 400 エラー（prompt is too long）を返します（出典：Models overview、Context windows）。

    実験台：月額の見積もり

    つまみを動かすと、月額の目安が変わります。まず、ボタンで例の使い方を選んでください。1 トークンあたりの文字の係数は、日本語では公式の値がないので、仮定の値です。自分の文章で数えた値に置き換えると、見積もりが現実に近づきます。

    見積もりを読むときの注意が 3 つあります。1 つ目は、履歴を毎回送ると、会話が進むほど、1 回の入力が増えることです（第 04 章）。2 つ目は、キャッシュの書き込みなどの追加の費用は、この実験台に含まれないことです。3 つ目は、為替は仮定で、実際の請求は、ドルで行われることです（出典：Pricing の請求の説明は「すべてドル」）。

    月の上限と、レート制限の例

    第 02 章の「利用の上限」には、段階（tier）ごとの上限があります。公式のレート制限のページが示す、月の上限は、次の表のとおりです。段階は、利用実績などから自動で決まり、時間とともに上がります。新しい組織は、この表より低い制限から始まることがあります（出典：Rate limits）。

    主なパラメータ、エラーと制限

    仕組み所要 約45分

    この章で分かること

    1. 主なパラメータ（max_tokens、stop_sequences、stream、effort）の役目と、temperature が使えなくなったことを説明できる。
    2. stop_reason と、主なエラーの種類を読み分け、再試行してよいかを判断できる。
    3. レート制限の仕組み（RPM・ITPM・OTPM、429、retry-after）と、再試行の考え方を説明できる。

    前提：第 03 章（レスポンスの形）と第 05 章（制限の数字の表）。

    主なパラメータ

    リクエストの本文には、model・max_tokens・messages のほかに、任意のパラメータがあります。次の表で、主なものを確かめます（出典：Messages API reference、2026 年 11 月 18 日確認）。

    temperature は、新しいモデルでは使えません

    古い記事によく出てくる temperature、top_p、top_k は、Claude 4.7 以降のモデルではサポートされません。API バージョン 2026-10-21 からは、すべてのモデルで、値を付けて送ると 400 エラーになります。公式は、これらをリクエストから外し、プロンプトで振る舞いを導くよう案内しています（出典：Working with Messages、API versions）。

    ストリーミング：答えを少しずつ受け取る

    長い答えは、完成を待つと、画面が止まって見えます。stream を有効にすると、答えがイベントの列として、少しずつ届きます。公式の Python SDK では、次のように書けます。

    import anthropic

client = anthropic.Anthropic()

with client.messages.stream(
    model="claude-haiku-5-5",
    max_tokens=1000,
    messages=[{"role": "user", "content": "短い自己紹介をしてください。"}],
) as stream:
    for text in stream.text_stream:
        print(text, end="", flush=True)

    流れは、次の図のとおりです。公式ドキュメントが示す順序で、message_start から message_stop まで、一手ずつ再生できます。

    stop_reason：なぜ止まったか

    レスポンスの stop_reason は、モデルが答えを止めた理由です。HTTP の状態は成功（200）でも、stop_reason が max_tokens や refusal のことがあるので、必ず確かめます。

    エラーの種類

    リクエストが失敗すると、HTTP の状態コードと、次の形の JSON が返ります。error.type と、request_id（サポートに問い合わせるときに使う識別子）が入ります（出典：Errors）。

    {
  "type": "error",
  "error": { "type": "not_found_error", "message": "…" },
  "request_id": "req_…"
}

    レート制限と、再試行の考え方

    レート制限は、1 分あたりに使える量の上限です。Messages API では、リクエスト数（RPM）、入力トークン数（ITPM）、出力トークン数（OTPM）の 3 つが、モデルごとに決まっています（数字の例は第 05 章）。どれか 1 つでも超えると、429 が返ります。公式ドキュメントによると、次の点が大事です（出典：Rate limits）。

    • 制限は、トークンバケット方式です。上限まで、容量が少しずつ回復し続けます。1 分ごとに、一斉にリセットされるのではありません。
    • 短い時間のバーストでも、制限に触れることがあります。急に使用量を増やすと、ランプ制限で 429 になることもあります。
    • 429 に retry-after ヘッダーがあるときは、その秒数待ってから再試行します。
    • 入力トークンのうち、キャッシュから読んだ分は、ITPM に数えません（第 10 章）。
    • 月の上限に達した 429 には、retry-after がなく、再試行しても、上限が戻るまで失敗します。

    再試行してよいかどうかは、エラーの種類で決まります。次の図で、判断の順序を追ってください。公式の SDK は、接続のエラー・408・409・429・5xx を、既定で 2 回、短い間隔を倍々にしながら自動で再試行します。max_retries で変えられます（出典：Python SDK）。

    import anthropic

client = anthropic.Anthropic(max_retries=3)  # 既定は 2 回。ここでは 3 回に増やす

try:
    message = client.messages.create(
        model="claude-haiku-5-5",
        max_tokens=1000,
        messages=[{"role": "user", "content": "こんにちは。"}],
    )
except anthropic.RateLimitError:
    print("429：待ってから、やり直す（月の上限なら、上限を確かめる）")
except anthropic.APIConnectionError:
    print("接続できませんでした")
except anthropic.APIStatusError as e:
    print("そのほかのエラー:", e.status_code)

    公式の SDK は、状態コードごとの例外のクラスを用意しています。たとえば、400 は BadRequestError、401 は AuthenticationError、429 は RateLimitError です。文字列を照合するのではなく、クラスで受けます（出典：Python SDK、Errors）。

    つまずきやすい点

    つまずきやすい点

    1 つ目は、stop_reason を見ないことです。max_tokens で切れた答えを、完成した答えとして使ってしまいます。2 つ目は、400 を再試行し続けることです。400 は、リクエストの形や内容の問題なので、直さない限り、何度送っても失敗します。3 つ目は、月の上限の 429 を、一時的な混雑と思うことです。メッセージと error.details.error_code で見分けます。

    プロンプトの書き方と、構造化した出力

    広げる所要 約45分

    この章で分かること

    1. プロンプトの基本（明確に、文脈を添え、例を示し、XML タグで区切る）を、公式のガイドに沿って説明できる。
    2. 長い資料を入れるときの置き場所（資料は上、質問は最後）を言える。
    3. 答えを JSON の形にそろえる構造化した出力の書き方と、注意点を説明できる。

    前提：第 04 章（system と messages）。

    プロンプトの基本：新人に頼むつもりで書く

    プロンプト（prompt）は、モデルに渡す指示と材料の全体です。公式の「Prompting best practices」は、Claude を「優秀だが、あなたの職場の決まりを知らない新人」と考えるよう勧めています。確かめ方も具体的です。文脈の少ない同僚に、そのプロンプトを見せて、従ってもらう。同僚が迷うなら、Claude も迷う、というものです（出典：Prompting best practices、2026 年 11 月 18 日確認）。

    基本は 5 つです。次の表は、あいまいな依頼と、整えた依頼を並べたものです（例は架空）。

    • 明確に、直接に書く：順序や漏れが大事なときは、番号つきの手順にします。
    • 理由を添える：「省略記号を使わない」だけでなく、「音声で読み上げるので、省略記号は読めない」と書くと、モデルが意図を一般化できます。
    • 例を示す：公式は、3〜5 個の、関連があり、多様で、構造の見える例を勧め、<example> のタグで、指示と区別します。
    • XML タグで区切る：指示・文脈・入力を、それぞれのタグで囲むと、取り違えが減ります。タグの名前は、一貫して、内容を表す名前にします。
    • 役割を system に書く：1 文でも効果があります。

    プロンプトの層と、置き場所

    次の図は、プロンプトの部品を、上から並べたものです。公式は、長い資料（目安で 2 万トークン以上）を使うときは、資料を上に置き、指示と質問を最後に置くと、質が上がると書いています。テストで、最大で 30% 上がった、とあります。部品を押すと、書き方の例が出ます。

    <documents>
  <document index="1">（ここに、長い資料を入れる）</document>
</documents>

<instructions>
上の資料だけを根拠に、質問に答えてください。まず、根拠になる部分を引用してください。
</instructions>

<question>（ここに、質問を書く）</question>

    「まず、関連する部分を引用させる」は、公式が長い資料で勧める方法です。答えの根拠を、確かめやすくなります。

    出力の形を、指定する

    公式は、「してはいけないこと」より、「してほしいこと」を書くよう勧めています。たとえば、「マークダウンを使わない」より、「滑らかな段落の文章で書く」です。形式を、タグで指定する方法もあります。

    書き出しの指定（プレフィル）は使えません

    Claude 4.6 以降では、assistant の書き出しを指定する方法が使えず、400 になります（第 04 章）。形をそろえたいときは、次の「構造化した出力」か、system への指示を使います。

    構造化した出力：JSON の形をそろえる

    プログラムで答えを使うには、答えが決まった形の JSON であってほしいものです。「JSON で答えて」と頼むだけでは、形が崩れることがあります。構造化した出力（structured outputs）は、JSON Schema（JSON の形を決める書き方）を渡して、答えをその形にそろえる機能です。公式ドキュメントでは、リクエストの output_config.format に、type: "json_schema" と schema を書きます（出典：Structured outputs）。

    import json
import anthropic

client = anthropic.Anthropic()

schema = {
    "type": "object",
    "properties": {
        "company": {"type": "string"},
        "amount": {"type": "number"},
        "due_date": {"type": "string"},
    },
    "required": ["company", "amount", "due_date"],
    "additionalProperties": False,
}

response = client.messages.create(
    model="claude-haiku-5-5",
    max_tokens=1000,
    messages=[{"role": "user", "content": "次の請求書の文面から、会社名・金額・支払期限を抜き出してください。\n\n（ここに、架空の文面を入れる）"}],
    output_config={"format": {"type": "json_schema", "schema": schema}},
)

if response.stop_reason == "end_turn":
    text = next(b.text for b in response.content if b.type == "text")
    data = json.loads(text)
    print(data)
else:
    print("形が完成していない可能性：", response.stop_reason)

    公式は、Pydantic のモデルを渡す client.messages.parse() を、推奨の方法としています。注意点も、公式に書かれています。

    つまずきやすい点

    つまずきやすい点

    1 つ目は、構造化した出力でも、中身の正しさは保証されないことです。形は schema どおりでも、金額の読み違いはありえます。人の確認や、コードでの検算を置きます（第 12 章）。2 つ目は、stop_reason を見ずに JSON を読むことです。max_tokens で切れたり、refusal だったりすると、schema に合わないことがあります。3 つ目は、プロンプトを直感だけで直すことです。直す前後を、同じ例で比べる評価（第 06 章）を、少しでも置きます。

    広げる所要 約45分

    この章で分かること

    1. ツールの利用で、モデルが道具を実行するのではないことを説明できる。
    2. tool_use と tool_result のやり取りを、順に言える。
    3. 自分で動かす道具（クライアントツール）と、Anthropic 側で動く道具（サーバーツール）を区別できる。

    前提：第 04 章（messages）、第 07 章（stop_reason）。

    ツールの利用とは

    モデルは、文章を作ることは得意ですが、あなたの会社の在庫表を見に行くことはできません。そこで、道具（ツール）の名前と使い方を、リクエストに書いて渡します。モデルは、必要だと判断すると、「この道具を、この引数で使ってほしい」という依頼を返します。道具を実際に動かすのは、あなたのプログラムです。結果をモデルに返すと、モデルはそれを材料に、最後の答えを作ります（出典：Tool use overview、2026 年 11 月 18 日確認）。

    一番大事な点

    モデルは、道具を呼ぶ「依頼書」を書くだけです。実行するかどうか、何を許すかは、あなたのコードが決めます。第 13 章の安全の話は、ここが出発点です。

    流れを、順に動かして確かめる

    次の図は、在庫を調べる道具を使う 1 往復です（例は架空）。ステップを進めると、各段階でやり取りされる中身が見えます。

    道具の定義と、やり取りの部品

    道具は、tools の配列に、name（名前）、description（説明）、input_schema（引数の形を表す JSON Schema）で書きます。description は、モデルが「いつ使うか」を決める手がかりなので、丁寧に書きます。strict: true を付けると、呼び出しの入力が schema に合うことを保証できます。

    コードで書くと

    次の例は、上の流れをそのままコードにしたものです。道具の本体（get_stock）は、あなたの側にあり、表は説明用の架空のものです。繰り返しには、回数の上限を置いています。このコードは、構文の検査だけをして、API を呼んで動かしてはいません。

        "description": "商品コードを受け取り、在庫の数を返す。在庫の数だけを調べる道具で、注文はできない。",
        "input_schema": {
            "type": "object",
            "properties": {"code": {"type": "string", "description": "商品コード（例：A-100）"}},
            "required": ["code"],
        },

    table = {"A-100": 12, "B-200": 0}  # 説明用の架空の在庫表
    return str(table.get(code, "該当なし"))

            )
    messages.append({"role": "user", "content": results})

    画像と PDF を渡す

    第 04 章で、user の content は「ブロックの一覧」にできると学びました。画像は image ブロック、PDF などの文書は document ブロックで渡します。渡し方は 3 通りで、base64 で本文に埋める、URL で指す、Files API で先にアップロードして file_id で指すです（出典：Vision、PDF support、2026 年 11 月 18 日確認）。公式は、画像や PDF を、文章より先に置くと、うまく働くとしています。

    PDF は、各ページが画像に変換され、文字も取り出されて、両方がモデルに渡されます。そのため、図や表の読み取りもできます。そのぶん、ページが多いと入力トークンが増え、費用も増えます。サイズやページ数の上限は、変わりやすいので、公式の各ページで確かめてください（この講座には数字を書きません）。

    画像の読み取りには、限界があります

    公式は、小さい・回転した・画質の低い画像では精度が落ちること、数や座標の出力はおおよそであること、画像から人の名前を特定しないことを挙げています。重要な用途では、出力を必ず確かめます（第 12・13 章）。

    費用と時間の工夫：2 つの道具

    同じ長い資料を何度も渡す、件数が多い、といった場面には、2 つの工夫があります。単価の数字は第 05 章の表にあります。ここでは、仕組みと使い分けだけを学びます。

    プロンプトキャッシュ：同じ前置きを再利用する

    リクエストの先頭側（tools、system、messages の順）が、前回と1 文字も違わず同じなら、その部分を再利用して、読み取りの料金を安くできます。cache_control の印を付けた場所までが、再利用の対象です。公式の説明では、既定の保存時間は 5 分で、1 時間にもできます。短すぎる入力は、エラーにならず、単に使われません（最小の長さはモデルごとに違います）。効いたかどうかは、usage の cache_creation_input_tokens（書き込み）と cache_read_input_tokens（読み取り）で確かめます。両方が 0 なら、使われていません。

    バッチ処理：急がない大量の仕事を、まとめて頼む

    Message Batches API は、たくさんのリクエストを、まとめて非同期で処理します。公式の説明では、費用が安くなる代わりに、結果はすぐには返りません。ほとんどは 1 時間以内に終わりますが、保証ではなく、24 時間で打ち切られます。結果は順番どおりとは限らないので、各リクエストにつけた custom_id で突き合わせます。ストリーミングは使えません。

client = anthropic.Anthropic()

SAFE_TOOLS = {"get_stock"}  # 確認なしで動かしてよい、読むだけの道具
MAX_STEPS = 8  # 繰り返しの上限
MAX_TOKENS_TOTAL = 20000  # 使ってよい出力トークンの合計の上限


def run_tool(name, args):
    if name == "get_stock":
        return "12"  # 架空の結果
    return "未対応の道具です"


def ask_human(name, args):
    answer = input(f"道具 {name} を {args} で実行してよいですか？ (y/n) ")
    return answer.strip().lower() == "y"


def run_agent(task, tools):
    messages = [{"role": "user", "content": task}]
    used = 0
    for _ in range(MAX_STEPS):
        response = client.messages.create(
            model="claude-haiku-5-5", max_tokens=1000, tools=tools, messages=messages
        )
        used += response.usage.output_tokens
        if response.stop_reason != "tool_use":
            return response  # 終わり
        if used > MAX_TOKENS_TOTAL:
            raise RuntimeError("使用量の上限に達したので、中断します")
        messages.append({"role": "assistant", "content": response.content})
        results = []
        for block in response.content:
            if block.type != "tool_use":
                continue
            if block.name in SAFE_TOOLS or ask_human(block.name, block.input):
                results.append({"type": "tool_result", "tool_use_id": block.id, "content": run_tool(block.name, block.input)})
            else:
                results.append({"type": "tool_result", "tool_use_id": block.id, "content": "利用者が実行を断りました", "is_error": True})
        messages.append({"role": "user", "content": results})
    raise RuntimeError("回数の上限に達したので、中断します")

    response = client.messages.create(
        model=model,
        max_tokens=max_tokens,
        system=system,
        messages=[{"role": "user", "content": user}],
        **extra,
    )
    if response.stop_reason == "max_tokens":
        raise RuntimeError("答えが途中で切れました。max_tokens を見直してください")
    return next(b.text for b in response.content if b.type == "text")
