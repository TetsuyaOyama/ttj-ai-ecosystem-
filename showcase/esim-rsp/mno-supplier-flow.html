MNO × SIMサプライヤー：プロファイル生成・納品フロー

QRコードが利用者に届く「前段」の裏側です。MNOからの発注（Input File）に始まり、サプライヤーでのキー生成とプロファイル生成、納品（Output File）、そしてMNO側での回線管理登録と認証登録までを追えます。コンシューマ（SGP.22）・IoT（SGP.31/32）・M2M（SGP.01/02）はボタンで切り替えられます。

STEP 1

補足1やり取りされるファイルの形式と中身

Input File（発注）

形式は CSV／固定長テキストが今も主流で、SFTP や専用線で受け渡します。中身は発注番号、ICCID の採番レンジ（IoT では EID リスト）、IMSI、プロファイル種別（USIM の構成）、PIN／PUK の方針、数量、納期などです。

Output File（納品）

形式は CSV／固定長。中身は ICCID、IMSI、Ki（暗号化）、PIN1／PUK1、PIN2／PUK2、ADM キーなど。IoT では EID が対応表の先頭キーになります。鍵データは暗号化して渡すことが前提です。

プロファイル本体

SIMalliance の相互運用フォーマット（ETSI TS 102 226 系の TLV 構造）で組み立てられます。eSIM として配布されるときは、SGP.22／SGP.32 の BPP（Bound Profile Package：ASN.1 DER 符号化＋暗号化）の形になります。

API 方式（ES2+）

MNO と SM-DP+ の間では、注文・確定・解放を ES2+ でオンライン処理する方式も標準化されています。ただし大量一括の製造現場では、ファイル方式が今も併用されています。M2M（SGP.02）では、EUM→SM-SR の ES1、SM-DP⇔SM-SR の ES3、SM-SR⇔eUICC の ES8 という専用のインターフェース群を使います。

補足2方式が変わると何が変わるか

SGP.31 はアーキテクチャと要件（eIM・IPA の役割分担やユースケース）を定めた文書で、SGP.32 はその技術仕様です。2つは対になっていて、流れそのものは1つです。
