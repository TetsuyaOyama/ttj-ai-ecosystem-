この章で分かること

  1. サーバーのファームウェアの種類（UEFI〔Unified Extensible Firmware Interface〕、BMC〔基板管理コントローラ〕、ネットワークカード〔NIC〕・SSD〔Solid State Drive、フラッシュメモリの記憶装置〕・GPU〔Graphics Processing Unit、AI 計算向けの演算装置〕など）と、電源投入から OS が動くまでの流れを、順に説明できる。
  2. PXE（Preboot Execution Environment）と HTTP ブート（HTTP は Hypertext Transfer Protocol、ウェブの通信の約束）の違いを、何で起動ファイルを取るかで言い分けられる。
  3. ファームウェアを一括で更新するときの順序・確認・戻し方の考え方を説明できる。

前提：第19章（基板管理コントローラ〔BMC〕と Redfish）。第06章（CPU サーバーの中身）を読んでいると、部品の位置が分かりやすくなります。

この章で「公開情報で確認できた範囲」

規格の名称・版・公開時期は、UEFI Forum と DMTF の公開ページで確認しました。UEFI 仕様書は、冒頭・目次・ネットワーク起動の章を確認し、全文は読んでいません。更新の失敗と回復の具体的な作りは、製品ごとに違い、公開資料の範囲も限られます。そのため、一般的な考え方として書き、製品の仕様としては書いていません。

ファームウェアは、機器ごとに入っている

ファームウェア（firmware）は、機器の中に書き込まれ、その機器を動かす基本のソフトウェアです。サーバーには、ファームウェアを持つ部品がいくつもあります。

  • UEFI ファームウェア：電源投入後に最初に動き、機器を初期化して OS を起動する。従来の BIOS に代わるもの（製品の画面では「BIOS」の名前が残ることがある）。
  • BMC のファームウェア：第19章の管理のコントローラを動かす。
  • NIC・SSD・GPU などのファームウェア：それぞれの部品が自分の動作に使う。

どれも、OS の外にあり、版を管理して更新する必要があります。版が合わないと、起動できない、部品が認識されない、性能が出ないなどの問題が起きます。下の表は、種類ごとの更新の経路と、失敗したときの影響の一般論です。製品で例外があります。

UEFI と ACPI：OS とファームウェアの約束

UEFI（Unified Extensible Firmware Interface）は、OS とプラットフォームのファームウェアの間の標準のインターフェースです。ファームウェアが OS へ渡す情報の表と、起動や実行中に OS が呼べる機能を決めています。目的は、機器が違っても、標準の OS が機器ごとの手直しなしに起動できるようにすることです。従来の PC-AT 型の起動環境から移ることも狙っています（出典：UEFI Forum『UEFI Specification 2.11』、第 1 章）。

UEFI 仕様は、UEFI Forum が策定します。2.11 版は 2024 年 12 月に、プラットフォーム初期化（Platform Initialization, PI）仕様の 1.9 版とともに公開されました（出典：UEFI Forum の発表、2024 年 12 月）。UEFI Forum の仕様一覧には、執筆時（2026 年 11 月）、UEFI 仕様が 2.11 版、PI 仕様が 1.10 版（2026 年 7 月）と載っています（出典：UEFI Forum『Specifications』）。

ACPI（Advanced Configuration and Power Interface）は、OS が機器を設定し、電力を管理するための、ハードウェアとソフトウェアのインターフェースとデータの形を決めた仕様です。ファームウェアが、機器を説明する表を OS へ渡します。ACPI 仕様も UEFI Forum が持ち、6.6 版が 2025 年 5 月に公開されています（出典：UEFI Forum『ACPI Specification 6.6』、『Specifications』）。

電源投入から OS まで

電源を入れてから OS が動くまでには、いくつもの段階があります。UEFI ファームウェアの中は、PI 仕様が SEC、PEI、DXE、BDS などの段階を決めています。PEI の段階は、メモリを使える状態にして、DXE の段階へ引き継ぎます。DXE の段階は、機器の初期化の大部分を行います。BDS の段階は、コンソールと起動する機器を準備し、OS を起動できる状態にします（出典：UEFI Forum『UEFI PI Specification 1.8』第 2 章）。下の図で、一連の流れを一手ずつ追ってください。

図の「自己診断」は、POST（Power-On Self-Test）と呼ばれる、電源投入時の機器の確認です（第19章の HTTP の操作の名前「POST」とは別の意味です）。メモリや拡張機器が正しく見えるかを調べます。名前と画面表示は、製品によって違います。異常があると、BMC のログ（第19章）や画面の表示に残ります。

ネットワークで起動する：PXE と HTTP ブート

台数が多いサーバーは、機器の中のストレージではなく、ネットワーク越しに起動することがあります。OS の導入や、同じ OS を多数の機器で動かすときに便利です。UEFI 仕様は、そのための方法を 2 つ定めています（出典：UEFI Specification 2.11、第 24 章）。

PXE（Preboot Execution Environment）は、DHCP（Dynamic Host Configuration Protocol、ネットワーク設定を自動で配る仕組み）で機器のネットワーク設定と起動サーバーの場所を知り、TFTP（Trivial File Transfer Protocol、簡単なファイル転送の約束）で起動ファイルを受け取ります。HTTP ブートは、起動するファイルの URL を指定し、DHCP で設定を得て、必要なら DNS（Domain Name System、名前から住所を引く仕組み）で名前を引き、HTTP でファイルを受け取ります。HTTP ブートは UEFI 2.5 で導入されました。UEFI Forum の 2015 年の講演資料は、PXE が使う TFTP には暗号化と認証がなく、遅く、損失に弱いことを課題に挙げ、HTTP ブートは HTTPS（HTTP を TLS で暗号化したもの）による保護と TCP（Transmission Control Protocol、確実に届ける通信の約束）による確実な転送を使えると説明しています（出典：UEFI Forum の講演資料『Goodbye PXE, Hello HTTP Boot』、2015 年 10 月 7 日。説明は講演者の資料の表現）。

どちらを使うかは、機器と、起動サーバー側の環境で決まります。起動ファイルを受け取る通信は、OS が動く前に行われます。保護の仕組みを別に考える必要があります。起動の安全は、第25章でまとめます。

起動の設定は、台数が増えると手作業では済まない

UEFI には、設定の項目があります。性能に関わるもの、電力に関わるもの、仮想化の機能を使うかどうかに関わるものなどです。項目の名前と選択肢は、製品によって違います。

台数が少ないうちは、機器の画面で 1 台ずつ設定できます。台数が増えると、設定のずれが起きます。起動の順序、仮想化の設定、電力の設定が、機器によって違うと、同じ OS とアプリケーションが、機器によって違う動きをします。そのため、設定も、第19章の管理インターフェースを使い、管理ツールから一括で行います。設定を宣言して、そろえる考え方は第21章です。

ファームウェアを一括で更新する

ファームウェアの更新は、1 台ずつ手で行うこともできますが、台数が多いと一括で行います。Redfish には、更新を扱うUpdateServiceがあります。DMTF の白書は、次の点を説明しています（出典：DMTF『Redfish Firmware Update White Paper』DSP2062 1.2.0、2026 年 4 月 3 日）。

  • FirmwareInventory：OS の外で動くプラットフォームのファームウェアの一覧。
  • 更新の方法：イメージの場所を渡して機器が取りに行く方法（SimpleUpdate）と、クライアントがイメージを送り込む方法（push）がある。push のうち、複数の部分を使う形式が推奨で、動作が各社の定義に任される古い方法は非推奨とされている。
  • 順序：機器を更新する順序は、サービス側が決め、並行して更新することが多い。順序の指定（StepOrder）は任意で、詳細な依存関係の仕組みは白書の範囲外である。
  • 適用の時期：イメージを置いておき、あとで有効にする（Stage）ことや、いつ適用するか（即時、再起動時、メンテナンス時間の開始時など）を指定できる。

つまり、規格は更新の入口を決めていますが、どの部品をどの順で更新するかの依存は、運用側が管理するのが現実です。たとえば、新しい UEFI ファームウェアが、新しい版の BMC の機能を前提にすることがあります。製品の資料で、更新の組合せと順序を確認します。

更新の失敗と回復：二重化された領域

ファームウェアの更新は、途中で電源が落ちる、イメージが壊れている、版が合わない、などの理由で失敗することがあります。失敗すると、機器が起動しなくなることがあります。そこで、ファームウェアを保存する領域を二重化して、更新中も動作する版を残す設計があります。更新に失敗したら、元の版へ戻せます。これがロールバック（rollback）です。二重化の有無と、戻し方は、製品によって違います。

運用側でもできる備えがあります。更新の前に現在の版を記録する、一度に更新する台数を絞る、更新後に版と動作を確認する、などです。全台を一度に更新すると、不具合があったときに、全台が同時に止まります。段階的に進める考え方は、第21章の変更管理でも扱います。

起動のときにファームウェアが自分を確かめる仕組み（セキュアブート）と、更新の改ざんを防ぐ仕組みは、第25章で扱います。ここでは、UEFI 仕様に「Secure Boot and Driver Signing」の章があることだけを示します（出典：UEFI Specification 2.11 の目次）。

演習：更新計画の順序と、止める条件を選ぶ

次は、顧客 C 社の 20 台のサーバーを、更新する計画です。ファームウェアは 3 種類で、BMC、UEFI、NIC です。値はすべて架空です（出典：架空、見本のため）。

  • BMC の新しい版：UEFI の新しい版を管理するために必要。
  • UEFI の新しい版：新しい BMC を前提にする。NIC の新しい版とも組み合わせて確認済み。
  • NIC の新しい版：UEFI の新しい版とは独立に更新できる。

問い：更新する順序を決めてください。また、更新を止めて調べる条件を、2 つ挙げてください。

答えを見る

順序は、BMC → UEFI → NICです（NIC は先でも後でもよい）。UEFI の新しい版が、新しい BMC を前提にしているので、BMC を先に更新します。

止める条件の例：(1) 最初の少数の台数（たとえば 2 台）の更新後の確認で、版が想定と違う、または起動しない機器が 1 台でもあったとき。(2) 更新の後に、BMC のログ（第19章の SEL）に、想定外のエラーが記録されたとき。いずれも、残りの台数へ進む前に原因を調べます。

少数の台数で試してから、残りへ広げるのは、不具合が全台に広がるのを防ぐためです。

つまずきやすい点

UEFI と BIOS は、同じものを指す言葉として使われることがあります。厳密には、UEFI は仕様の名前で、BIOS は従来の PC の起動環境の名前です。製品の資料では、画面や設定項目が「BIOS」のままの場合もあります。仕様の名前と製品の呼び名を分けて読みます。

もう 1 つ。更新が「完了」と表示されても、新しい版がまだ動いていないことがあります。適用が再起動のときに行われる設定の場合、再起動するまで、古い版が動いたままです。更新の後は、版を読み直して確認します（第19章の Redfish で読める）。

現場でのつながり

機器の立上げ（第28章）では、出荷時の版が、顧客の指定する版と違うことがあります。受入の前に版をそろえる作業が要るため、段取りに時間を見込みます。運用では、更新の計画を第21章の変更管理に載せ、第23章の監視で更新後の異常を見ます。
