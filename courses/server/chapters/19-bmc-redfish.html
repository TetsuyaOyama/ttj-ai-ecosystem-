  2. IPMI（Intelligent Platform Management Interface）と Redfish（DMTF が定めた管理の規格）の違いを、何を決めた規格かで言い分けられる。
  3. Redfish の URI（Uniform Resource Identifier、リソースの住所）とリソース（Systems・Chassis・Managers・UpdateService など）を読み、電源状態と温度の警告を取り出せる。

この章で「公開情報で確認できた範囲」

規格の名称・版・公開日は、DMTF（Distributed Management Task Force、標準化団体。Redfish を定めた）と、IPMI の仕様書の公開版で確認した範囲だけを書きました。Redfish のリソースの意味と電源状態の値は、DMTF の『Redfish Resource and Schema Guide』（2022.3 版）で確認しました。各社の BMC の機能は、製品と版で違います。この章は規格の考え方の説明で、特定の製品の設定手順ではありません。

BMC は、サーバーの中の「留守番係」

基板管理コントローラ（Baseboard Management Controller, BMC）は、サーバーの基板に載る小さなコントローラです。温度や電圧などの状態を見張り、出来事を記録し、遠くからの操作に応じます（出典：Linux Foundation の発表、2018 年 3 月）。

IPMI の仕様書は、この仕組みが扱う範囲を次のように示しています。温度・電圧・ファンの監視、復旧の動作、出来事の記録（イベントログ）、警報の通知、機器の在庫情報です（出典：IPMI v2.0 仕様書、第 1 章、Rev 1.1、2013 年 10 月）。まとめると、BMC の主な仕事は次の 5 つです。

  • 電源の操作：電源を入れる、切る、再起動する。
  • センサーの監視：温度、電圧、ファンの回転、電源ユニットの状態を読む。
  • ログの記録：異常や操作の履歴を残す。IPMI ではシステムイベントログ（System Event Log, SEL）と呼ぶ。
  • リモートコンソール（remote console）：離れた場所から、画面やキーボードの代わりに操作する。画面を扱うものは「仮想 KVM」とも呼ぶ。機能の有無と呼び名は製品で違う。
  • ファームウェアの更新：BMC 自身や、機器のファームウェアを入れ替える（第20章）。

BMC が役に立つのは、ホストの CPU や OS が動いていないときです。電源が切れた状態でも、一部の部品には補助の電力が残ります（出典：DMTF『Redfish Resource and Schema Guide』DSP2046 の電源状態の説明、2022.3 版）。多くの BMC は、この待機の電力で動き、本体が止まっていても応じます（一般的な設計の説明です。製品の詳細は各社の資料を確認してください）。

帯域外管理：データの道とは別の道で管理する

サーバーが利用者のために通信するネットワークを、ここでは「データの道」と呼びます。管理の操作を、この道と OS の中で行うと、OS が止まったときに手が届きません。そこで、BMC に専用のネットワーク口をつけ、別の道から操作します。これが帯域外管理（out-of-band management）です。管理用の道を管理ネットワークと呼びます。

Redfish の仕様書も、範囲を「複数のメーカーにまたがり、遠隔から使え、帯域外にも対応できるインターフェース」と書いています（出典：DMTF『Redfish Specification』DSP0266 1.23.0、2025 年 9 月 5 日）。IPMI の仕様書は、実行中のソフトウェアの助けなしに警報を出せることと、LAN・シリアル・PCI Management Bus から常に管理できることを目標に挙げています（出典：IPMI v2.0 仕様書、第 1 章）。

下の図で、3 つの見方を切り替えてください。「管理」では運用者の操作がどこを通るか、「データ・信号」では BMC とホストの関係、「電力」では待機の電力の流れを示します。

管理ネットワークは、データのネットワークと分けて作るのが基本です。BMC には電源操作やファームウェア更新の権限があるからです。分け方と認証の考え方は第25章で扱います。

IPMI：命令と記録の形を決めた規格

IPMI（Intelligent Platform Management Interface）は、サーバーの管理の仕組みを標準にした規格です。バージョン 2.0 は、4 社が 2004 年 2 月 18 日に発表しました。認証と暗号化の強化、LAN 越しにシリアル端末を使う Serial over LAN（SOL）などが加わりました（出典：Intel の発表資料、2004 年 2 月）。現在読める仕様書は、v2.0 の Rev 1.1（2013 年 10 月 1 日）と、訂正をまとめた補遺（E6、2014 年 2 月 11 日）です（出典：Intel の公開資料）。

IPMI が決めているのは、共通の命令、イベントの形式、データの記録（センサーの記録、機器の在庫情報など）です。仕様書の目次には、SEL の命令と記録形式、SDR（Sensor Data Record、センサーの記録）、FRU の在庫情報、SOL、RMCP+（LAN 越しの認証つき通信）が並んでいます（出典：IPMI v2.0 仕様書、目次）。

IPMI は長く使われてきたので、いまも多くの機器で出会います。一方で、命令と記録の形式を一つずつ決める作りです。これに対して Redfish は、Web の一般的な道具の上で、機器の状態を「リソース」として決めています。次の節で見ます。IPMI を使えるかどうかは、機器と BMC の版で違います。各社の資料で確認してください。

Redfish：Web の作りで、管理を表す規格

Redfishは、DMTF（Distributed Management Task Force）が策定した管理の規格です。仕様書 DSP0266 の 1.0.0 は 2015 年 8 月 4 日の公開で、この章の執筆時に確認できた版は 1.23.0（2025 年 9 月 5 日）です（出典：DMTF の DSP0266 の版の一覧と仕様書）。機器の状態を表す「スキーマ」の束（DSP8010）は、2026.1 版が 2026 年 4 月 2 日に公開されています（出典：DMTF『Redfish Schema Bundle Readme』DSP8010、2026.1）。2026 年 11 月 14 日に DMTF の版の一覧を見直すと、DSP0266 は 1.24.0（一覧の日付は 2026 年 5 月 17 日。仕様書の表紙の日付は 2026-04-02）まで公開されています。この章の記述（HTTP/1.1・JSON・必須の操作など）は 1.23.0 に基づき、1.24.0 での変更点は確認していません。スキーマの束にも、新しい版が出ていることがあります。DMTF の公開ページで確認してください。

Redfish の作りは、次の 4 点です（出典：DSP0266 1.23.0）。

  • 通信：HTTP（Hypertext Transfer Protocol、ウェブの通信の約束）のバージョン 1.1 の上で動く。暗号化は TLS（Transport Layer Security、通信を暗号化する仕組み）で行う。
  • データの形：JSON（JavaScript Object Notation、項目と値の組を文字で表す形式）で表す。すべてのリソースは JSON で取れる。
  • 約束事：URL の作り方や共通の項目に、OData の考え方を取り入れている。
  • 操作：GET（読む）、POST（作る・操作を実行する。HTTP の操作の名前で、第20章の電源投入時の自己診断「POST」とは別の意味）、PATCH（一部を変える）、DELETE（消す）は必須。PUT・HEAD・OPTIONS は任意。

入口は /redfish/v1/ です。URI の「v1」はプロトコルのメジャーバージョンを表します。ここから、リンクをたどって他のリソースへ進めます。サービスルートと /redfish の資源は、認証なしで読める決まりです。そのほかは、セッションの認証（X-Auth-Token）などで守ります（出典：DSP0266 1.23.0）。

IPMI と Redfish の違いを、表で並べます。どちらが優れるかではなく、何を決めた規格かを見てください。

Redfish のリソースを読む

Redfish のリソースは、URI で表します。下の図で、URI の部分を押してください。コレクション（同じ種類の集まり）と、その中の 1 つのリソースに分けて読みます。

サーバーの管理でよく見るリソースは、次の 5 つです。

Redfish の主なリソース（出典：DMTF『Redfish Resource and Schema Guide』DSP2046 2022.3、『Redfish Firmware Update White Paper』DSP2062 1.2.0）
リソースURI の例表すもの
Systems/redfish/v1/Systems/{ComputerSystemId}計算機としてのシステム。メモリ、プロセッサなど、使える資源へのリンクを持つ。電源状態（PowerState）と電源の操作（Reset）もここにある。
Chassis/redfish/v1/Chassis/{ChassisId}筐体、ラックなど、物としての入れ物。センサーなど、データの通り道の外にある部品も、ここにつながる。
Managers/redfish/v1/Managers/{ManagerId}Redfish のサービスを動かす、または入口になる管理の主体。BMC や、筐体の管理モジュールが当たる。
UpdateService/redfish/v1/UpdateServiceファームウェアとソフトウェアの更新の入口。ファームウェアの一覧（FirmwareInventory）へのリンクと、更新の方法を持つ（第20章）。
EventService/redfish/v1/EventService出来事の通知の入口。通知の申込み先（Subscriptions）と、Server-Sent Events の受け口を持つ（第23章）。

Chassis の下には、センサーのリソースがあります。センサーは、読み値（Reading）、種類（ReadingType。温度、電圧、電力など）、単位（ReadingUnits）、状態（Status）、しきい値（Thresholds）を持ちます。しきい値には、注意の上限（UpperCaution）と、危険の上限（UpperCritical）があります（出典：DSP2046 2022.3）。この章の演習は、この形を読む練習です。

電源状態：Redfish が決めた値

電源を入れる操作は、いきなり完了しません。切れた状態から、動いている状態になるまでに、移行の途中があります。Redfish の PowerState は、この途中も値として持ちます。2022.3 版の説明では、値は Off、On、Paused、PoweringOn、PoweringOff の 5 つです。PoweringOn と PoweringOff は、切替えの途中の一時的な状態です（出典：DSP2046 2022.3）。その後の版で、Sleeping と Hibernating が足されています（出典：DMTF DSP8010 2026.1 の変更履歴。Resource スキーマ 1.24.0）。

電源の操作は、Reset のアクションに、ResetType を渡して行います。値には、すぐ切る ForceOff、OS に終了を頼んでから切る GracefulShutdown、OS に終了を頼んで再起動する GracefulRestart、すぐ再起動する ForceRestart、電源を入れる On などがあります（出典：DSP2046 2022.3）。「すぐ切る」と「OS に頼んで切る」は、結果が違います。前者は、OS が書き込み中のデータを守れません。

Redfish で電源を入れる 1 回

運用者が管理ツールを使って、電源を入れる流れを追います。HTTP の動きと、BMC の中の動きを、順に見てください。値はこの章の説明用の例です。

BMC の種類と OpenBMC

BMC は、サーバーメーカーが自社の製品に合わせて作るのが一般的です。Dell Technologies（米国）は iDRAC（Integrated Dell Remote Access Controller）を、Hewlett Packard Enterprise（HPE、米国）は iLO を、それぞれの BMC の呼称として使っています。どちらも Redfish の API を公開しています（出典：Dell Technologies『iDRAC: Redfish API with Dell integrated Remote Access Controller』、HPE の iLO の Redfish 資料）。名前と機能は製品で違うので、ここでは例として挙げるだけで、比べません。

一方、BMC のファームウェアを共通の部品で作る動きもあります。OpenBMC は、BMC のファームウェアのオープンソースの共通基盤です。Linux Foundation が 2018 年 3 月 19 日に、IBM が提供したコードを土台にして発足を発表しました。機器が違っても使える、共通の BMC ファームウェアを作る狙いです（出典：Linux Foundation の発表、2018 年 3 月 19 日）。

演習：Redfish の応答から、警告の出ている部品を読み取る

次は、架空のサーバー（顧客 C 社の機器）の応答の一部です。値はすべて架空です（出典：架空、見本のため）。項目の名前は、Redfish のセンサーのリソース（Reading、ReadingType、Status、Thresholds）に合わせています。読みやすくするため、しきい値の入れ子は簡略にしてあります。単位も省いています。

GET /redfish/v1/Chassis/1U/Sensors/Inlet
{ "Name": "吸気温度", "ReadingType": "Temperature", "Reading": 24,
  "Status": { "State": "Enabled", "Health": "OK" } }

GET /redfish/v1/Chassis/1U/Sensors/CPU1
{ "Name": "CPU1 温度", "ReadingType": "Temperature", "Reading": 91,
  "Thresholds": { "UpperCaution": 85, "UpperCritical": 95 },
  "Status": { "State": "Enabled", "Health": "Warning" } }

GET /redfish/v1/Chassis/1U/Sensors/DIMM3
{ "Name": "DIMM3 温度", "ReadingType": "Temperature", "Reading": 62,
  "Thresholds": { "UpperCaution": 85, "UpperCritical": 95 },
  "Status": { "State": "Enabled", "Health": "OK" } }

問い：警告が出ているのはどのセンサーですか。その値は、注意と危険の上限に対してどの位置ですか。吸気温度が正常なことは、何を示しますか。

答えを見る

警告は CPU1 のセンサーです。Health が Warning で、読み値 91 は、注意の上限 85 を超え、危険の上限 95 には届いていません。

吸気温度は 24 で正常です。部屋から入る空気は問題なく、CPU1 だけが熱いことを示します。原因は、機器の中の風の通り道（ファン、エアシュラウド）や、CPU のヒートシンクの接触などを疑います（第06章）。DIMM3 は正常です。次に、同じ筐体のファンのセンサーの値を調べます。

つまずきやすい点

帯域外管理は、ネットワークをつなぐだけでは安全になりません。BMC は、電源の操作やファームウェアの更新ができる強い権限を持ちます。初期の認証情報のまま使う、データのネットワークと同じ道に置く、といった使い方は避けます。分離と認証の考え方は第25章です。

もう 1 つ。Redfish を使える機器でも、すべてのリソースを持つとは限りません。規格は「必須の部分」と「任意の部分」を分けています。実際に使えるリソースは、その機器の応答（サービスルートからたどった結果）で確かめます。

現場でのつながり

機器を選ぶとき、BMC が対応する管理インターフェース（IPMI、Redfish）の版を、仕様書で確認します。運用では、第21章の構成管理が Redfish で機器を登録・更新し、第23章の監視が BMC のセンサーとログを集めます。商談では「帯域外の管理ネットワークは顧客側が用意するか」が、設置前の取り合いになります（第31章）。
