### 0.1 内容の決まり（全章共通・変えない）

1. **公開情報だけ**を使う：規格団体（PCI-SIG、USB-IF、VESA、JEDEC、UEFI Forum、SATA-IO、NVM Express、TCG、Wi-Fi Alliance、Bluetooth SIG、IEEE、HDMI の規格の管理団体）の公開資料、部品メーカー・OS の提供者の公式資料（製品ページ・データシート・マニュアル・サポート記事・保証規定）、当局の公開資料（経済産業省、総務省、消費者庁、警察庁、製品評価技術基盤機構〔NITE〕、情報処理推進機構〔IPA〕など）、教科書的な一般知識。フォーラム・動画・個人のブログ・通販の商品説明・まとめサイトを根拠にしない。
2. **企業名・製品名は公開情報の範囲で実名可**。ただし**特定の製品・店・サービスを勧めない**（「◯◯がおすすめ」「◯◯社が優れる」「コスパが良い」と書かない）。示すのは、選び方の考え方と、確かめる項目と、確かめる資料の種類。製品の例を表に載せるときは、比較・順位を付けず、「例であり推奨ではない」と表の注記に書く。演習・ケースの人物・店・会社は**必ず架空**（「利用者 A さん」「販売店 B」「メーカー C」）。
3. **数字（消費電力、寸法、速度、容量、温度、騒音、保証期間、価格帯）には必ず出典と時点を付ける**。書式は `GLOSSARY-RULES.md` §5。確認できない数字は書かない（「目安」「一般に」で埋めない）。変わりやすい数字は確認問題・総合テストの正答にしない。
4. **価格**は変わりやすいので、**具体の金額は載せない**。予算の配分・電気代などの例は「架空」と明記した金額か割合だけを使う。**買い時の予想・値上がり値下がりの見通しは書かない**（第13章は、製品の世代と価格が動く仕組みの説明にとどめる）。
5. **安全に関わる内容**（電源ユニット・通電中の作業・コンセント、静電気、けが、リチウム電池、液冷の漏れ、定格を超える設定、負荷試験、データの消失）は、**してはいけないことと注意点を明記**し、該当する章に §9.3 の定型の注意書きを置く。電源ユニットの分解・修理、液冷の配管の分解・自作、電圧や倍率を手で変えて定格を超える設定、メーカーの保証を外れる改造（ヒートスプレッダの取り外しなど）の**手順は書かない**（存在と危険を言葉で示すだけ）。作業の具体は「各部品のマニュアルに従う」とし、マニュアルの代わりにならないと断る。
6. **ソフトウェアの不正利用は扱わない**：ライセンスの回避、非公式の認証、OS の動作要件を回避する方法、非公式の配布元からの入手、有料ソフトの不正な複製。言及もしない（「回避する方法がある」とも書かない）。
7. **法令・保証・取引**（古物営業法、電気用品安全法、電波法、消費者の契約、メーカーの保証規定）は、制度と規定の仕組みの説明にとどめ、個別の取引・製品の適否を判断しない。定型の注意書き（§9.3「価格・取引」）を置く。
8. **セキュリティ**（第17・18・24章）は守る側の仕組みと考え方だけ。攻撃の手順・脆弱性の悪用方法は書かない。
9. 正確さが最優先。確信のない細部は書かず、参照資料を示す。各章の「執筆時に Web で確認する事実」は、書く前に確認し、確認できたものだけ書く（§8.1 の事実確認表に残す）。★の付いた項目は、変わりやすいので**公開の直前にもう一度**確かめる（§8.2-10）。

## 1. 講座の狙い・読者・到達点

**狙い**：PC が「何の部品でできていて、部品どうしがどんな規格でつながり、電力と熱がどう流れるか」を土台に、用途に合わせて部品を選び、互換性・電力・冷却を自分で確かめ、安全に組み立て、起動・調整・不具合の切り分け・保守までを一人で進められるようにする。結論を覚えるのではなく、**どの資料のどこを見れば確かめられるか**を身につける。

**読者**：パソコンは使える（ファイル操作・ソフトの導入・設定画面の操作ができる）が、中身は詳しくない社会人。初めて自作する人、完成品の買い替えを機に自作を考える人、組んだことはあるが調整と保守に自信がない人。数式は四則演算だけ（第07章の W ＝ V × A、第12章の電力量と電気代、第07・12章の効率と負荷率。式は §9.4 が正）。

**読み終えた後にできること**

1. PC の 9 種類の部品（CPU、マザーボード、メモリ、ストレージ、グラフィックスカード、電源ユニット、ケース、クーラー、周辺の接続）の役割と、データ・電力・熱の流れを、部品の名前で 5 分で説明できる。
2. 「DDR5-6000」「M.2 2280 PCIe 4.0 x4 NVMe」「USB 10Gbps」「12V-2x6」のような表記を、規格・世代・形・速度のどれの話かに切り分けて読める。
3. 用途から要件表を作り、予算の配分の考え方を説明でき、ソケット・メモリの対応・寸法・電源ユニットの容量とコネクタの互換性を、メーカーの一次資料（仕様ページ・マニュアル・CPU サポートリスト）で確かめた確認表を作れる。
4. 部品の公開値から電力と熱の見積もりを組み立て、電源ユニットとクーラーの選び方の条件を言える。
5. 静電気と通電に注意して、正しい順序で取り付け・配線し、最初の起動・UEFI の設定・OS とドライバの導入・負荷試験・温度と騒音の調整を進められる。
6. 不具合を段階で切り分け、部品の交換と増設・掃除・バックアップを計画でき、ローカル AI・小型機・静音機の構成の考え方を説明できる。保証の窓口と、何を誰（販売店・メーカー・公的な窓口）に確かめるべきかが分かる。

## 6. 部品

### 6.1 新しい部品：なし

基盤の 17 種（`arch` `seq` `flow` `layers` `xsec` `route` `stack` `ident` `table` `tree` `state` `drill` `quiz` `compare` `mapping` `glossary` `exam`）だけで作る。検討した候補と結論：

- **互換性の自動判定**（部品を選ぶと適否が出る部品）→ 足さない。判定の正しさを講座が保証できず、製品の推奨にも近づく。互換性は `table`（確認表）・`ident`（脚注の解剖）・`flow`（確認の順序）・`drill`（ケース演習）で、読者が一次資料で確かめる力として扱う。
- **電力・電気代の計算器**→ 足さない。式は本文と `ident`（c12-bill）、計算は架空値の演習と確認問題で扱う（第2弾と同じ判断）。
- **ケース内の配置・空気の流れ**→ `layers`（c08-case）と `arch`（c08-airflow）で足りる。
- **熱の伝わる断面**→ `xsec` の固定の材料を `materials` で言い換えて使う（色は固定。足りない材料を作らない。第2弾の第16章と同じ使い方）。
- **保証の窓口**→ `route` で足りる。`mode` は輸送用の記号だが、店の区間は `store` に統一し、図の注記で「購入と保証の区間」と書く。


- **区分**（必ずどれか 1 つ）：`発表`（年月日・主体・共同の相手）／`企業`（社名の表記・本社の国・地域）／`制度`（法令・制度の名称・施行・改正・所管）／`規格`（名称・番号・**版・公表日**・発行者）／`仕様値`（製品の公開値と、**その値の名前**）／`安全`（安全の注意・禁止の根拠。メーカーのマニュアル・当局の注意喚起）／`保証`（保証規定・保証の扱い）／`定義`（用語・式）／`一般知識`（教科書的な内容。数値を伴うなら出典の教科書名を書く）。
- **一次**：`○` 発表の主体・規格団体・メーカー・当局自身の個別ページ／`△` 主体の原文を配信サービスが掲載したもの／`×` 報道・解説・まとめ・通販の商品説明。
- **高リスクの区分**（`発表` `企業` `制度` `規格` `安全` `保証`）は `○` か `△` だけで書く（第2弾より `規格` `安全` `保証` を足した）。`×` しか見つからないものは**書かない**。`仕様値` も原則 `○`（販売店のページの値を使わない）。
- 確認問題・総合テスト・図のデータの中の事実も表に載せる（`使った箇所` にデータ id）。
- 下書きでは、確認前の事実を本文に入れない。どうしても置くときは `【要確認】` の印を付け、表の行を作ってから外す。**ビルドの前に `grep -rn '要確認' chapters data facts` が 0 件**であること。

### 8.2 高リスクの事実の確認の仕方

第2弾の 1〜9 を引き継ぎ、10〜13 を足します。

1. **年月日**：原文の発信日・公布日・施行日・公表日を `YYYY-MM-DD` で写す。記憶・二次情報・検索結果の要約の日付を使わない。
2. **発表の主体**：原文の発信者と、共同発表の相手を原文で確かめる。
3. **企業の国**：各社の公式サイトの会社概要か IR の本社所在地で確かめる。日本法人・代理店の所在地と、本社の国を混同しない。
4. **制度**：名称・施行日・規模を、当局の個別ページの文言どおりに写す。「以上」「超」「未満」「以下」を言い換えない。
5. **主張の帰属**：根拠の資料が 1 つなら、主体は 1 つだけ書く。
6. **用語**：企業・団体の資料を引くときは、その資料の表記を使う（各社の呼称を一般名に言い換えない・一般名を各社の呼称に言い換えない）。
7. **一般化**：1 つの資料・1 つの製品の事実を「一般に」「どの製品でも」に広げない。マニュアルの指示は「◯社のマニュアルは〜と指示している」と書き、全製品の決まりにしない。
8. **現在性**：製品の提供状況・社名・団体の所管は変わる。社名の変更（第2弾 REVIEW-part3 M1）も確かめる。
9. **数値の換算**：単位換算・合計・比率を自分で計算した値は書かない（出典の値をそのまま書く）。演習の計算は架空値でだけ行う。
10. **規格の版**：規格の版は、**発行団体の公式の仕様のページ・発表のページ**で、現行の版と公表日を確かめる。百科事典・報道・製品ページの「◯◯対応」の表記から版を写さない。本文は「執筆時点（YYYY 年 M 月）で確認できた最新の版は ◯◯（YYYY 年 M 月公表）」と書く。団体のページで現行の版が確かめられないときは版を書かず、規格の名前だけにする。★の項目は、公開の直前に検証担当がもう一度開く。
11. **安全の記述**：安全の注意・禁止は、メーカーのマニュアル・サポート記事、当局（消費者庁・NITE・経済産業省・総務省消防庁）の注意喚起から書く。当局の注意喚起は、**最新の公表日の資料**を探してから使う（古い通知だけで書かない）。フォーラム・動画の通説を書かない。
12. **製品の仕様値**：値と一緒に**値の名前**（「TDP」「Processor Base Power」「総消費電力」など、メーカーの呼称のまま）と、測定・定義の条件を写す。名前の違う値を同じ列に並べるときは、列の見出しを「公開値（名前は行ごと）」にし、名前を値の前に書く。
13. **保証の扱い**：保証の対象・対象外は、各社の保証規定の文言どおりに写し、「保証が切れる」「保証の対象外になる」を言い換えない。1 社の規定を全社に広げない。

### 8.3 参照リンク

- 参照資料の表のリンクは、**その事実が載っている個別ページ**（仕様のページ、PDF、サポート記事、法令の条文のページ、注意喚起の発表）にする。公式サイトのトップ・製品一覧・ニュース一覧にしない（自己点検の 5 で機械的に検査する。§8.10）。
- 個別ページの URL を一次資料で確かめられないときは、その事実を書かない。
- 有料の規格（JEDEC の一部、IEC、ISO など）は、発行団体の公開ページ（概要・販売ページ）にリンクし、表の「この章での使い方」に「規格本文は読んでいない」かどうかを書く。
- 他章で確認済みの事実を使うときは、その章へのリンク（`#chNN`）にし、自分で数字を書き写さない（§9.1）。
- 参照資料の種類（付録の `c26-refs` の `filter` と揃える）は次の 6 区分だけ：**規格・仕様**／**団体の資料**／**メーカーの資料**（仕様ページ・マニュアル・サポート記事・保証規定）／**当局・公的機関**／**教科書・一般知識・他講座**／**架空（見本のため）**。第2弾で種類の誤分類が出たため（REVIEW-part5 M4）、迷ったら発行者で決める（団体が出した資料は「団体の資料」、規格そのものは「規格・仕様」）。

### 8.4 章の間の食い違いを防ぐ

- §9.1 の「事実の持ち主」の章だけが数字・定義を書く。持ち主でない章は、言葉で触れて持ち主の章へリンクする。
- 持ち主の章の担当は、確定した事実確認表を早めに共有し、他の担当はそれを読んでから書く（§7.3）。
- 用語の割り当ては `GLOSSARY-RULES.md` §8。図のラベル・本文・用語集の表記を一致させる。
- 計算サーバー講義と同じ語は同じ表記・食い違わない説明にする（`GLOSSARY-RULES.md` §10）。相互参照は §3 の 3 か所だけ。

### 8.5 確認問題・総合テスト・演習

**数と形**

- 確認問題は**各章ちょうど 3 問**、選択肢は**各問 4 個**。総合テストは §3 の数（1 問か 2 問）。
- **正答の添字（`a`）は次の式で決める**（第2弾と同じ式）：第 NN 章の k 問目（k＝1〜3）は `a = (NN + k − 1) mod 4`。例：第01章は 1・2・3、第02章は 2・3・0、第04章は 0・1・2。総合テストは `a = (NN + 2) mod 4`（2 問の章の 2 問目は `(NN + 3) mod 4`）、第26章の横断の 2 問は 0・1。

**書き方（正答の添字の誤りを防ぐ）**

1. 問ごとに、まず式で `a` を決める。
2. **正答の文を、配列の `a` 番目に最初に書く**。そのあと残りの位置に誤答を埋める（正答を 0 番に書いてから並べ替えない。第2弾の C1 は並べ替えの途中で正答と誤答が入れ替わった）。
3. `why` の最初の文に、正答の文の要点を書く（例：「正答は『各 CPU に直結したメモリと…』です。」）。自己点検の出力で、`問`・`正答`・`why` が同じことを言っているかを目で読む。
4. 正答が 1 つだけかを確かめる：誤答が別の読み方で正解にならないか（条件の書き忘れ、「〜だけ」「必ず」の有無）を、問題ごとに 1 回読み直す。
5. 位置に依存する選択肢（「上のすべて」「A と B」）、否定形の問い、変わりやすい数字（消費電力・価格・保証期間・規格の速度）を正答にする問題は作らない。
6. 解説（`why`）は正答の理由と、もっとも選ばれやすい誤答がなぜ違うかを書く。解説が本文の原則（例：一度に 1 つだけ変える、定格の範囲にとどめる、保証は規定で確かめる）と矛盾しないかを読み直す。

**演習（`drill`・並べ替え・計算）**

- 並べ替えの演習は、**提示の順を答えの順と変える**（答えが提示順と同じなら出題し直す）。
- `drill` の正答（段階・最初に調べる対象）は、同じ講座の他の図（`c17-seq`、`c21-tree`、`c11-flow`）と食い違わないかを、ケースごとに照らす。食い違ったら図の持ち主の章に合わせる。
- 計算の演習は、架空の値・式（§9.4）・答えを事実確認表の下の「定義と式の照合」（§8.6）にも書き、答えを 2 回計算する。

**機械での検証**：§8.10 の自己点検（3 の項目）を、章を書き終えるたびに走らせる。式どおりでない・選択肢が 4 個でない・`why` が無い問題は `NG` になる。`NG` が 0 件でも、出力された `問` と `正答` の組を全部目で読む（式では「正答の位置」は検査できても「その位置の文が正しいか」は検査できないため）。

### 8.6 定義と式の照合（式を使う章：07・12・19・その他、式や比を書く章すべて）

- 式は §9.4 が正。章で式を書くときは §9.4 の形を変えない（記号・単位・分子と分母の向き）。
- データファイルの事実確認表の下に、次の形の照合表を置く。**定義の文・式・用語集の説明・演習の答えの 4 つが同じことを言っているか**を 1 行ずつ確かめる（第2弾の M1 は、定義の文と式が別の定義を前提にしていた）。

```
定義と式の照合（第NN章）
| 量 | 本文の定義の文 | 式（§9.4 の番号） | 用語集の d | 演習・問の使い方 | 一致 |
|---|---|---|---|---|---|
| 負荷率 | 電源ユニットが出している電力の、定格出力に対する割合 | 式 4 | （同じ文） | 演習 2：架空の 300 W ÷ 600 W ＝ 50% | ○ |
```

- 用語集の `d` に式を入れない（`GLOSSARY-RULES.md` §7）。定義の言葉だけを、本文の定義の文と同じにする。
- 「約」「ほぼ」を付けた定義（例：消費電力はほぼすべて熱になる）は、出典の言い方どおりにし、演習では「熱 ＝ 消費電力とみなす（架空の前提）」と前提を明記する。

### 8.7 図の線の種別（`plane`）と色の種別（`kind`）

第2弾では、データの線に太線（`up`）や点線（`lg`）を使い、図の切替（`views`）で同じ線の種別が変わる誤りが 18 か所ありました（REVIEW-part1-2 M4）。

1. **線の種別は、その線が運ぶものだけで決める**（§6.2）：電力・空気・冷却液は `up`、データ・映像・制御信号は `cp`、設定・契約・保証・参照は `lg`。見た目の強調のために種別を変えない。
2. **`plane` を省略しない**（既定に頼らない）。どの線にも明示する。
3. **同じ線（同じ `id`）の種別を `views` で変えない**。電力と信号の両方を運ぶケーブル（ファンの 4 ピン、USB の給電、補助電源の検知の線）は、図の目的に合わせて 1 本の種別を選び、`carries` に両方を書く。両方を見せたいときは、電力の線と信号の線を**別の `id`** で 2 本引き、`views` で出し分ける（c16-wiring）。
4. §3 で線の種別を指定した図（c01-arch、c03-lanes、c04-channel、c06-power、c07-out、c08-airflow、c16-wiring、c26-map）は、その指定に従う。
5. `kind` は §6.2 の意味だけ。マザーボード・ケースは部品の「入れ物」なので、`kind` を付けずに `groups`（枠）で表す。
6. 自己点検（§8.10 の 4）が全部の線を `図 id・種別・端点・ラベル・運ぶもの` で出力するので、§6.2 の表と 1 行ずつ照らし、完了報告の自己点検表に「線の種別：全 n 本を確認」と書く。

### 8.8 略語の初出

第2弾では、章の冒頭の囲み（「この章で分かること」）に略語が英語併記より先に出ていました（REVIEW-part4 M7）。この講座では次のように決めます（`GLOSSARY-RULES.md` §3 と同じ）。

1. **「章の初出」は、章の HTML の先頭から数える**。冒頭の囲み・見出し・図のデータ（`CN.add` の文字列のうち、本文より先に読者の目に入るもの）を含む。
2. **冒頭の囲みと見出し（`<h3>` `<h4>`）には、まだ説明していない略語を出さない**。日本語で書く（「起動時の自己診断」「ビデオメモリ」）。どうしても出すときは、その場で正式名を併記する。
3. 略語は、章ごとの初出で `日本語（English full name, 略語）` か、略語が一般名になっている語は `略語（English full name）` の形にする（`GLOSSARY-RULES.md` §3.1）。他の章で定義済みでも、章ごとに併記する。
4. **一般的な IT の略語（HTTP・URL・LED・USB・SSD など）も対象**。併記を省いてよいのは `GLOSSARY-RULES.md` §3.4 の 4 語（PC・OS・AI・ID）だけ。
5. 図のデータの中（`seq` の `msg`、`flow` の工程名、`layers` の部位名）は短くするため略語可。ただし、その章の本文で、その図より前に初出の併記を済ませていること。
6. 自己点検（§8.10 の 6）が、括弧の近くにない初出の候補を出力する。候補はすべて目で確かめ、併記を足すか、既に併記済みであることを確かめる。

### 8.10 自己点検の道具（`pc-selfcheck.js`）

各担当は、次のスクリプトを `/tmp/pc-selfcheck.js` に写して使う（講座ディレクトリには置かない。node だけで動く）。章を書き終えるたび、`build.py --check` と一緒に走らせる。

```sh
node /tmp/pc-selfcheck.js /home/claude/courses/pc 03 --need c03-board,c03-lanes,c03-form,c03-chipset,c03-quiz
node /tmp/pc-selfcheck.js /home/claude/courses/pc 26 --apx 26 --need c26-map,c26-refs      # 付録
```

検査する内容：1 題・部・トラックが `course.json` と一致／2 登録したデータがすべて本文に置かれている、`--need` の id がデータにある／3 確認問題が 3 問・各 4 択・`why` あり・正答の添字が §8.5 の式どおり（問と正答の文を出力）、総合テストの添字が式どおり（付録は 0・1…）／4 構成図の全部の線を種別つきで出力／5 本文のリンクがトップページでない／6 略語の初出の候補（括弧が近くにないもの）を出力／7 「要確認」の印が残っていない。最終行が `NG 0 件` になるまで直す。

```js
// 自己点検: node /tmp/pc-selfcheck.js <講座ディレクトリ> <章番号> [--apx 付録の章番号] [--need id,id,…]
const fs = require('fs'), path = require('path'), vm = require('vm');
const argv = process.argv.slice(2), opt = k => { const i = argv.indexOf(k); return i < 0 ? '' : argv[i + 1]; };
```

| 式 6 | bit と byte | 1 byte ＝ 8 bit | 転送速度の換算は bit と byte の換算だけ。符号化の損失を含む実効の速度は計算しない（出典の値を使う） | 01・05・09 |
| 式 7 | 容量の 10 進と 2 進 | 1 GB ＝ 1,000,000,000 byte、1 GiB ＝ 1,073,741,824 byte | 製品の表示は 10 進。OS の表示の単位は OS 提供者の説明で確かめてから書く | 05 |

熱の量は「消費電力とほぼ同じ」（出典の言い方どおり）とし、熱の計算の式（風量と温度差）はこの講座では扱わない（計算サーバー講義の第15章の範囲。リンクもしない。相互参照を 3 か所に保つため）。
