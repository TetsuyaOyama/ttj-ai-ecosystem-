この章で分かること

  1. 主なパラメータ（max_tokens、stop_sequences、stream、effort）の役目と、temperature が使えなくなったことを説明できる。
  2. stop_reason と、主なエラーの種類を読み分け、再試行してよいかを判断できる。
  3. レート制限の仕組み（RPM・ITPM・OTPM、429、retry-after）と、再試行の考え方を説明できる。

前提：第 03 章（レスポンスの形）と第 05 章（制限の数字の表）。

主なパラメータ

リクエストの本文には、model・max_tokens・messages のほかに、任意のパラメータがあります。次の表で、主なものを確かめます（出典：Messages API reference、2026 年 11 月 18 日確認）。

temperature は、新しいモデルでは使えません

古い記事によく出てくる temperature、top_p、top_k は、Claude 4.7 以降のモデルではサポートされません。API バージョン 2026-10-21 からは、すべてのモデルで、値を付けて送ると 400 エラーになります。公式は、これらをリクエストから外し、プロンプトで振る舞いを導くよう案内しています（出典：Working with Messages、API versions）。

ストリーミング：答えを少しずつ受け取る

長い答えは、完成を待つと、画面が止まって見えます。stream を有効にすると、答えがイベントの列として、少しずつ届きます。公式の Python SDK では、次のように書けます。

import anthropic

client = anthropic.Anthropic()

with client.messages.stream(
    model="claude-haiku-5-5",
    max_tokens=1000,
    messages=[{"role": "user", "content": "短い自己紹介をしてください。"}],
) as stream:
    for text in stream.text_stream:
        print(text, end="", flush=True)

stop_reason：なぜ止まったか

レスポンスの stop_reason は、モデルが答えを止めた理由です。HTTP の状態は成功（200）でも、stop_reason が max_tokens や refusal のことがあるので、必ず確かめます。

エラーの種類

リクエストが失敗すると、HTTP の状態コードと、次の形の JSON が返ります。error.type と、request_id（サポートに問い合わせるときに使う識別子）が入ります（出典：Errors）。

{
  "type": "error",
  "error": { "type": "not_found_error", "message": "…" },
  "request_id": "req_…"
}

レート制限と、再試行の考え方

レート制限は、1 分あたりに使える量の上限です。Messages API では、リクエスト数（RPM）、入力トークン数（ITPM）、出力トークン数（OTPM）の 3 つが、モデルごとに決まっています（数字の例は第 05 章）。どれか 1 つでも超えると、429 が返ります。公式ドキュメントによると、次の点が大事です（出典：Rate limits）。

  • 制限は、トークンバケット方式です。上限まで、容量が少しずつ回復し続けます。1 分ごとに、一斉にリセットされるのではありません。
  • 短い時間のバーストでも、制限に触れることがあります。急に使用量を増やすと、ランプ制限で 429 になることもあります。
  • 429 に retry-after ヘッダーがあるときは、その秒数待ってから再試行します。
  • 入力トークンのうち、キャッシュから読んだ分は、ITPM に数えません（第 10 章）。
  • 月の上限に達した 429 には、retry-after がなく、再試行しても、上限が戻るまで失敗します。

再試行してよいかどうかは、エラーの種類で決まります。次の図で、判断の順序を追ってください。公式の SDK は、接続のエラー・408・409・429・5xx を、既定で 2 回、短い間隔を倍々にしながら自動で再試行します。max_retries で変えられます（出典：Python SDK）。

import anthropic

client = anthropic.Anthropic(max_retries=3)  # 既定は 2 回。ここでは 3 回に増やす

try:
    message = client.messages.create(
        model="claude-haiku-5-5",
        max_tokens=1000,
        messages=[{"role": "user", "content": "こんにちは。"}],
    )
except anthropic.RateLimitError:
    print("429：待ってから、やり直す（月の上限なら、上限を確かめる）")
except anthropic.APIConnectionError:
    print("接続できませんでした")
except anthropic.APIStatusError as e:
    print("そのほかのエラー:", e.status_code)

公式の SDK は、状態コードごとの例外のクラスを用意しています。たとえば、400 は BadRequestError、401 は AuthenticationError、429 は RateLimitError です。文字列を照合するのではなく、クラスで受けます（出典：Python SDK、Errors）。

つまずきやすい点

つまずきやすい点

1 つ目は、stop_reason を見ないことです。max_tokens で切れた答えを、完成した答えとして使ってしまいます。2 つ目は、400 を再試行し続けることです。400 は、リクエストの形や内容の問題なので、直さない限り、何度送っても失敗します。3 つ目は、月の上限の 429 を、一時的な混雑と思うことです。メッセージと error.details.error_code で見分けます。
